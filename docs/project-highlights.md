# 项目亮点介绍（2026-10 版）

> 所有数字都来自仓库里的评测脚本与结果文件，括号内标注了出处，面试前可直接打开对照。

## 一句话定位

针对健身爱好者训练数据碎片化、知识获取低效、缺乏趋势分析三大痛点，构建基于 ReAct Agent 与 RAG 的健身 AI 教练：用户用自然语言提问或描述训练，Agent 自主判断意图并调度训练记录、历史查询、进展分析、知识检索、长期记忆五类工具，必要时多步调用后汇总作答——问"最近深蹲有进步吗、怎么突破平台期"，它会先查历史、再算力量趋势、最后检索训练方法；知识库侧支持上传文档，经分块、向量化、混合检索与精排后给出带出处的回答。

> 核心是我自己搭的一套**可评测**的 RAG + Agent 链路——每个技术决策都有对照实验，包括三个被实验否掉的方案。

## 简历版（4 条，前置一行项目概述）

> 项目概述（可放在项目名下面一行）：基于 LangGraph 的健身 AI 教练，5 个工具覆盖训练记录、历史查询、趋势分析、知识问答与跨会话记忆，前后端 + 评测链路完整。

1. **RAG 检索链路**：稠密向量 + BM25（jieba 分词）双路混合召回，再用 BGE-reranker-v2-m3 精排；自建 60 条口语化 query 的评测集上，相比纯稠密 Recall@5 +3.3pt、MRR +12pt，精排后 MRR 达 0.963；候选数从 40 降到 15，重排延迟 5.1s → 0.54s。

2. **长期记忆**：LLM 异步提取 + 4 维加权评分（相关性/特异性/未来有用性/非冗余性），仅 importance ≥ 0.6 写入 Qdrant，检索时叠加分类型指数时间衰减（半衰期 14–90 天）；存储噪音率 15.4%，偏好召回 Recall@5 63.3%、MRR 0.71。

3. **HITL 人工确认**：训练记录落库前插入确认断点，暂停等待用户确认、并可修正解析结果后再写入；确认状态持久化在 Postgres，服务重启后仍能从中断处恢复执行（跨进程验证通过，重复确认返回 409 防重）。

4. **上下文窗口管理**：窗口本身宽裕（1M），压缩的目的是控成本而非防溢出——超 60k tokens 清掉旧工具输出只留最近 3 条（检索片段跨轮无效），超 200k 将历史摘要为结构化画像并保留最近 12 条；阈值按中文 token 比折算。

## 30 秒口述版

> 我做了个健身 AI 教练，用 LangGraph 编排了 5 个工具，重点在检索和记忆两条链路上。检索是稠密 + BM25 双路融合，用 jieba 修了 Qdrant 中文不分词的问题，Recall 比纯稠密高 3 个多点、排序质量高 12 个点；再加 BGE 精排，MRR 到 96%，同时把候选数从 40 降到 15、重排从 5 秒压到 0.5 秒。记忆这块用 LLM 打分过滤后落 Qdrant，噪音率 15%；写训练记录前 Agent 会暂停等我确认，这个暂停状态存 Postgres，重启也不丢。

## 2 分钟版（面试展开）

**问题**：健身人群的训练数据散在备忘录里，想要"我最近深蹲进步了吗"这种回答，需要同时查数据库、算趋势、查知识库。

**做法**：LangGraph 的 ReAct 循环 + 5 个工具，工具描述就是路由依据；检索走"入库 → 召回 → 精排"三段，记忆走"提取 → 打分 → 衰减"三段。

**证据链（我最想讲检索这条）**：
- 一开始我用文档标题当 query，稠密检索 Recall 直接 1.0，指标饱和、什么都测不出。换成 LLM 读正文生成的改写问题后才有区分度，才看出 Hybrid 比 Dense 强在哪。
- 同一个配置重跑两次，MRR 差 0.006——这是 Qdrant 近似检索的噪声。有了这个基准，我才敢说 +12pt 是真的、而 +0.8pt 不是。
- 精排那一档也做了取舍：候选数从 40 降到 15，依据是覆盖率曲线（K=15 时理论上限还有 95.8%），效果没掉、延迟降到 1/10。

**如果被问路由**（这题现在不写进简历，但要有准备）：5 个工具时整体准确率 26.7%，漏调 0 次但误调 21 次。原因是工具描述偏"触发式"，且加了"记录训练"之后，任何提到训练内容的陈述句都可能触发它。改进方向是把工具描述改成排除式、合并两个查询类工具——评测集已就位，改完能直接回归。

## 四个"可以被问倒但我有答案"的地方

这部分比堆数字更值钱——它们证明结论是实验得出的，不是拼凑的。

### 1. Contextual Retrieval 做了，但没收益，所以默认关闭

给每个 chunk 生成文档级上下文前缀后再入库，是实现过的完整链路。实测（60 query）：稠密 Recall 0.858→0.850，混合 0.892→0.883，均略降；只有 BM25 微弱上升。

原因：我的文档本身是结构化写作，每个 chunk 开头就带 `## 二、具体做法` 这样的小节标题，上下文信息已经隐含在分块里；再叠一层 LLM 生成的前缀，等于给稠密向量掺入重复语义。这个技术真正适合的是"从长文档切出来的、没有局部结构的小 chunk"。

### 2. 中文分块修复是防御性的，在这套语料上没有收益

原来分隔符是 `["\n\n", "\n", ".", "!"]`，全英文标点。我对比了两个集合的 chunk 哈希：**60/60 篇完全一致**——因为段落都短于 750 字，`\n\n` 一级就已经切开了。

它修的是长段落场景：造一段 3000 字不分段的中文，旧配置会把"2.5 公斤"切成"…加重 2"和".5 公斤"，新配置切在"2.5 公斤"之后。所以这是正确性修复，不是性能提升。

### 3. 重排不是"把对的从 40 条里挑出来"，而是"把对的往前挪"

候选从 40 降到 15，Recall 反而从 0.892 升到 0.908——因为重排把原本排在第 6–15 名的相关文档拉进了前 5。这解释了为什么"少喂候选"没有代价：粗筛的前 15 名已经覆盖了 95.8% 的相关文档，第 16–40 名几乎从不翻盘。

---

### 4. 路由精度是当前最大的短板，而且我知道为什么

5 个工具时整体准确率 26.7%，误调 21 次。原因有两层：
- 工具描述偏"触发式"（"当用户询问营养时使用"），模型倾向于见到相关词就调，而不是判断"是否真的需要"；
- 加入 `add_workout_tool` 后，任何提到训练内容的句子都可能触发它，哪怕用户只是在陈述而不是要求记录。

改进方向（还没做）：工具描述改成"只在 X 且 Y 时调用"的排除式写法、把 query_workout 和 analyze_progress 合并成一个带 `mode` 参数的工具、在 system prompt 里加"闲聊不动工具"的显式约束。评测集就位，改完可以直接回归。

## 附：这次改造中修掉的真实 bug

写进简历容易，但面试被追问"你怎么发现问题的"时，这些是素材：

1. **批量上传重复入库**：边写边嵌，处理第 N 个文件时会把 tmp 目录里前 N-1 个文件再嵌一遍，3 个 PDF 让第一个文件入库 3 次。
2. **`reps` 语义矛盾**：工具文档写"每组次数"，数据结构按"总次数"存，LLM 照文档传值 → 5 组 5 次被记成总次数 5。
3. **评测脚本的重排分支从未跑通**：`get_reranker` 返回 `(docs, scores)` 元组，脚本当列表用，一跑到 BGE 模式就 AttributeError。
4. **`.gitignore` 的 `lib/` 误伤 `frontend/src/lib`**：整个前端工具目录从未进过版本库。
5. **建集合会隐式下载模型**：`set_sparse_model` 让 qdrant_client 自己初始化一份 fastembed，离线环境下建集合就失败。
