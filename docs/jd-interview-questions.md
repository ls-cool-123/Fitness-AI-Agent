## 一、AIGC 工具实操（ComfyUI / Stable Diffusion / 视频生成）

### Q1. 你用过 ComfyUI 吗？能说说你搭过的一个工作流吗？节点是怎么连的？

**答案要点（结合真实使用，讲一个具体工作流）：**

> 如果你真的搭过，讲你搭过的那个；如果没搭过，诚实说明并展示你**已经动手研究过**（比如本地装过、跑通过文生图基础流程），然后讲一个标准工作流。

**标准文生图工作流示例**（展示你懂节点逻辑）：
```
Load Checkpoint（加载 SD 大模型）
    ↓
CLIP Text Encode（正面提示词）→  ┐
CLIP Text Encode（负面提示词）→  ├→ KSampler（采样器，控制 denoise/CFG/步数）
Latent Image（空潜空间，设置宽高）→ ┘
    ↓
VAE Decode（把潜空间解码回像素图）
    ↓
Save Image（保存）
```

**关键节点理解**（面试官会追问）：
- **Checkpoint**：SD 大模型（如 SD1.5、SDXL），决定画风基底
- **CLIP Text Encode**：把提示词编码成模型能理解的向量，正面/负面分开
- **KSampler**：核心采样节点，参数有 `steps`（步数）、`cfg`（提示词遵循度）、`denoise`（重绘幅度，图生图时用）、`sampler_name`（采样器如 Euler、DPM++）
- **VAE**：潜空间和像素空间的转换器，解码质量影响成图清晰度
- **ControlNet**（进阶）：用姿态/线稿/深度图控制生成结构，适合电商模特换装、姿势控制

**加分回答**：主动说"我理解 ComfyUI 相比 WebUI 的优势是**节点化、可复用、可编程**，工作流本质是 DAG，可以导出 json 分享，也方便批量跑图"。

### Q2. 本地部署 Stable Diffusion 你遇到过什么问题？怎么解决的？

**答案要点（展示排障能力，这是 JD 最看重的"本地化优化、插件调试"）：**

常见问题与解决思路（挑 2-3 个讲）：
1. **显存不足（OOM）**：降低分辨率、减小 batch size、用 `--medvram`/`--lowvram` 参数、开启 xformers 优化、用 fp16 精度
2. **模型下载慢/失败**：配置 HuggingFace 镜像（`HF_ENDPOINT=https://hf-mirror.com`）、手动下载模型放到 models 目录
3. **插件冲突/版本不兼容**：ComfyUI 插件和核心版本不匹配导致报错，用 `git pull` 更新核心、逐个禁用插件二分定位
4. **出图质量差（崩图/黑图）**：检查 VAE 是否缺失、CFG 是否过高、采样器选择、负面提示词是否完整
5. **中文提示词支持差**：用翻译插件或直接写英文提示词，配合 tag 补全插件

**加分回答**：把"本地部署"和你 Fitness 项目的 Docker 经验结合——"我在 Fitness 项目里用 Docker Compose 编排了 5 个服务（Qdrant/MySQL/Phoenix 等），对容器化部署、数据卷挂载、服务编排很熟，这套经验可以直接迁移到 SD/ComfyUI 的本地部署上"。

### Q4. Seedance 2.0、即梦、可灵这些视频生成产品，你了解它们的区别吗？怎么选型？

**答案要点（展示你对前沿 AIGC 产品的持续跟进，这是 JD 第 2 条"主动追踪新技术"的体现）：**

## 二、AI Agent 平台与智能体搭建（Coze / Dify / 提示词工程）

> 这是 JD 第 4 条的核心要求。你已经有 LangGraph 搭建 Agent 的硬核经验，这是**降维打击**——面试官问 Coze/Dify 时，你要展示"我不仅会用低代码平台，还懂底层原理"。

### Q5. 你用过 Coze 或 Dify 吗？和直接用 LangGraph 写代码比，各有什么优劣？

**答案要点（展示你懂底层原理，这是你的最大优势）：**

**Coze/Dify（低代码平台）的优势**：
1. **上手快**：可视化编排，不用写代码，业务同学也能搭
2. **内置插件生态**：大量现成工具（搜索、图片、语音等）开箱即用
3. **发布方便**：一键发布到微信、飞书、抖音等渠道
4. **内置知识库/工作流**：RAG、多 Agent 编排都有可视化界面

**Coze/Dify 的局限**：
1. **定制化受限**：复杂逻辑、特殊数据源、私有化部署受限
2. **黑盒**：底层 prompt、模型调用细节不可控
3. **成本**：平台有调用配额/费用，高频场景成本高
4. **数据安全**：数据经过平台，敏感业务不适合

**LangGraph 写代码的优势**（你的强项）：
1. **完全可控**：状态管理、错误处理、上下文窗口、记忆策略全部自己掌控
2. **可评测**：能跑 Recall/MRR/路由准确率等量化指标（你在 Fitness 项目里做了）
3. **可集成**：能接 Qdrant、MySQL、Redis 等自建基础设施
4. **可扩展**：MCP、自定义工具、多 Agent 编排（你在 CareerPilot 里做了）

**结论**：**低代码平台适合快速验证和业务同学自助搭建；自研代码适合核心业务和深度定制。** 我两个都会用——用 Coze/Dify 快速验证想法，用 LangGraph 做生产级落地。

### Q6. 提示词工程你有哪些实践经验？怎么写出高质量的提示词？

**答案要点（结合你两个项目的真实 prompt 经验）：**

**核心方法论**：
1. **角色设定**：明确 AI 的角色（如"你是资深健身教练"）
2. **任务明确**：说清楚要做什么、输出什么格式
3. **约束条件**：限制范围、格式、语气（如"只输出 JSON"）
4. **示例引导（Few-shot）**：给 1-2 个输入输出示例
5. **结构化输出**：要求输出 JSON/表格，方便程序解析

**你的真实案例**（面试时讲这个最有说服力）：
- **Fitness 项目**：记忆提取的 `SCORING_SYSTEM_PROMPT`（`src/agent/memory/extractor.py`）——让 LLM 按相关性 0.35、特异性 0.25、未来有用性 0.25、非冗余性 0.15 四个维度给候选记忆打分，只保留 ≥0.6 的入库。这就是**结构化评分提示词**的典型应用
- **Fitness 项目**：工具 docstring 就是"路由提示词"——每个工具的描述决定了 LLM 是否调用它，我通过优化 docstring 提升路由准确率
- **CareerPilot 项目**：DeepEval 的 GEval 用 criteria 定义评测维度，本质也是提示词工程

**加分回答**：主动说"提示词工程不是玄学，要**可评测、可迭代**。我在 Fitness 项目里用路由评测集（15 条 query）验证 prompt 改动对路由准确率的影响，用数据说话而不是凭感觉调"。

## 三、本地部署 / 算力调配 / 流程迭代

### Q8. 你理解"本地部署环境维护、算力调配"具体是做什么的？你有哪些相关经验？

**答案要点（展示你对"AI 生产链路"的理解 + 你的 Docker/部署经验）：**

**本地部署环境维护**包括：
1. **环境管理**：Python 虚拟环境、依赖版本锁定（uv/conda）、CUDA/驱动版本匹配
2. **服务编排**：用 Docker Compose 编排多个服务（模型服务、向量库、数据库、前端）
3. **资源监控**：GPU/CPU/内存/磁盘监控，及时扩容或清理
4. **模型管理**：模型下载、版本管理、缓存管理（HuggingFace 缓存）
5. **日志与排障**：服务日志、错误追踪、快速定位问题

**算力调配**包括：
1. **GPU 分配**：多任务共享 GPU、显存管理、batch size 调优
2. **推理优化**：量化（fp16/int8）、模型缓存、批处理
3. **任务调度**：重计算任务放后台队列，避免阻塞主流程

**你的真实经验**（面试时讲）：
- **Fitness 项目**：用 Docker Compose 编排 5 个服务（agent/streamlit/mysql/qdrant/phoenix），配置数据卷持久化、服务依赖、环境变量——这就是"本地部署环境维护"的实战
- **Fitness 项目**：BGE 重排模型用模块级单例缓存（只加载一次），控制推理延迟——这就是"算力调配/推理优化"
- **CareerPilot 项目**：Redis 缓存分析结果（15-45s → <50ms），Redis 不可用时静默降级——这就是"流程优化 + 容错"

### Q11. 你遇到过什么技术难题？怎么解决的？如果解决不了怎么办？

**答案要点（用 STAR 法则讲一个真实案例，展示抗压能力和解决问题的能力）：**

**推荐案例（Fitness 项目的 jieba + BM25 中文分词问题）**：
- **S（情境）**：Fitness 项目用 Qdrant 的 BM25 做稀疏检索，但发现中文检索效果很差
- **T（任务）**：定位问题并优化中文检索效果
- **A（行动）**：排查发现 Qdrant 的 BM25 默认按空格分词，中文整句被当成一个 token，导致检索失效。我研究后写了一个 `JiebaBM25Sparse` 包装类，在调用 BM25 前先用 jieba 分词，索引端和查询端都走同一套分词逻辑，保证一致性
- **R（结果）**：混合检索召回率提升到 97.6%，MRR 提升到 93%

**如果解决不了怎么办**（展示正确的求助方式）：
1. 先自己查文档、搜社区、看源码，定位问题边界
2. 带着"我已经排查了哪些、试了哪些方案"去请教别人，而不是空手问
3. 如果短期解决不了，先给一个**临时降级方案**保证主流程可用，再持续优化

**加分回答**：主动说"我遇到问题会先看源码，比如为了搞懂 DeepEval 为什么需要 log_probs，我直接去看了它的源码，理解了它的评分逻辑，才能设计出适配层绕过它"——展示你**能深入源码**解决问题的能力。

**这份 JD 和纯技术岗面试的区别**：
