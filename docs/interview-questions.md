# AI 应用开发实习生面试问题 — 基于简历项目深度追问

> 定位说明：这份题库不是"八股文"，而是围绕你简历中的每一个技术 claim 进行**深度验证**的追问。
> 面试官看重的不是"你做了什么"，而是"你是不是真的懂为什么这么做、有没有踩过坑、换一种场景会不会做"。
> 每个问题后标注了考察意图，方便你针对性准备。

---

## 一、Fitness AI Agent — ReAct Agent 与工具路由

### 1.1 基础概念层

**Q1. 用你自己的话解释 ReAct 模式，它和单纯的 Chain/Sequential 调用的本质区别是什么？**

> 考察点：是否理解 Agent 的"思考-行动-观察"闭环，而不是只会套 LangGraph 的模板。

**Q2. 为什么选 LangGraph 而不是 LangChain 原生的 AgentExecutor？LangGraph 的 StateGraph 相比它的核心优势是什么？**

> 考察点：技术选型时是否做过对比，还是跟随教程。

**Q3. 你的 Agent 会根据用户意图路由到"训练查询 / 进展分析 / 知识库搜索"3 个工具。这个路由是 LLM 自主决策（ReAct 推断）还是代码层面的硬编码规则？如果用户一句话同时涉及两个工具的意图，会发生什么？**

> 考察点：路由机制的实现细节。简历说"复杂多工具联动场景覆盖率 100%"——**100% 是个危险数字**，面试官一定会追问这个数字怎么测的、边界在哪。

### 1.2 深度追问层

**Q4. "工具召回率 100%"这个指标具体是怎么定义的？测试集有多少条？覆盖了哪些场景？如果遇到 Agent 陷入死循环（反复调用同一个工具），你的系统有什么兜底机制（如 max_iterations、循环检测、递归限制）？**

> 考察点：指标的严谨性。任何"100%"的指标在面试官眼里都是红旗，要么测试集太小，要么指标定义有问题。

**Q5. Agent 调用工具返回异常（数据库连接失败、Qdrant 超时、工具产出非法 JSON）时，你的错误处理链路是什么？是会重试、还是直接把这个错误喂回给 LLM 让它自己想办法，还是降级到失败回复？**

> 考察点：生产级 Agent 和最基础 Demo 的分水岭就在错误处理。

**Q6. 三个工具里，"训练查询"和"进展分析"都涉及数据库操作。你是让 Agent 直接生成 SQL/Mongo 查询（Text-to-SQL），还是预定义了固定查询函数？如果是 Text-to-SQL，你怎么防注入？怎么保证 LLM 生成的 SQL 是安全的？**

> 考察点：LLM 与数据库交互的安全边界设计。

## 二、Fitness AI Agent — 混合检索 RAG（稠密 + BM25）

### 2.1 基础概念层

**Q7. 为什么做混合检索？纯稠密检索（如 BGE embedding）最大的弱点是什么？纯 BM25 稀疏检索最大的弱点又是什么？请给一个具体的健身领域例子，说明各自失效的场景。**

> 考察点：对两种检索范式的本质理解。不能只背"语义理解 vs 关键词匹配"。

**Q8. 解释 BM25 的公式。`k1` 和 `b` 两个超参数分别是干什么的？在 Qdrant 里用的默认值是多少？**

> 考察点：是否真的懂 BM25，还是只知道"BM25 是稀疏检索"。

### 2.2 中文分词优化（核心追问点）

**Q9. 你说 Qdrant 的 BM25 只用英文空格分词，对中文是整句一个 token，导致效果差。请具体解释：jieba 分词是怎么接入 Qdrant BM25 管线的？是改 Qdrant 配置、还是在索引前就做分词的预处理？如果是预处理，检索时的 query 也要同样分词吗？查询端和索引端分词不一致会导致什么问题？**

> 考察点：这是你简历里最"藏细节"的一个点。面试官非常有可能追问实现层面——**你到底是在 Qdrant 侧配置了分词器，还是自己在代码里先 jieba 再塞进去？** 如果答不清，会被判定为"只看了文档没动手"。

**Q10. jieba 有精确模式、全模式、搜索引擎模式三种分词方式，你用的哪种？jieba 对专有名词（如"卧推""硬拉""深蹲"这种健身术语）分词不准怎么办？你为此准备自定义词典了吗？**

> 考察点：中文 NLP 的实际工程经验。

### 2.3 融合与评测

**Q11. 稠密检索结果和 BM25 结果你是怎么做融合的？用的是 RRF（Reciprocal Rank Fusion）还是加权分数？如果是 RRF，`k` 值取的多少？如果是加权，权重怎么定的？**

> 考察点：混合检索的融合策略是实现中最容易敷衍的部分。

**Q12. "双路检索相比纯稠密检索召回率提升 2.5%至 97.6%，MRR 提升 5.4%至 93%"——请告诉我：**
- **这个评测集是你自己标的还是公开数据集？多少条 query？**
- **Recall 是 Recall@多少？MRR 的倒数排名是对哪个候选列表算的？**
- **Baseline 的稠密检索用了什么 embedding 模型？**

> 考察点：指标真实性。面试官大概率会怀疑这些数字的来源。如果答不出评测集规模和质量控制，前面吹的指标全部作废。

## 三、Fitness AI Agent — BGE 重排序

**Q13. 为什么要引入重排序模型？既然第一轮混合检索已经做到 97.6% 召回，为什么还不够？**

> 考察点：召回和精排的两阶段思想。

**Q14. BGE-reranker-v2-m3 是 Cross-Encoder 结构，你需要把 query 和每个候选文档拼起来过一遍模型。Qdrant top-k 你取了 50 个候选，重排一次要多长时间？你怎么控制重排序的延迟？如果候选只有 10 个，还有必要重排吗？**

> 考察点：对重排模型计算代价和收益权衡的理解。

**Q15. "BGE 重排后 MRR 从 93% 提升到 96%"——请解释为什么重排能提升 MRR？重排模型"看到了"什么信息是第一轮检索看不到的？**

> 考察点：Bi-Encoder 与 Cross-Encoder 的信息交互差异。

## 四、Fitness AI Agent — 长期记忆模块

### 4.1 设计层

**Q16. 你说原始项目只有 MemorySaver 进程内短期记忆，系统一重启上下文全丢。你做的长期记忆，"长期"体现在哪儿？记忆存到 Qdrant，那 Qdrant 本身的持久化是怎么保证的（Docker volume？）？**

> 考察点：记忆模块的持久化链路。

**Q17. 你的"4 维加权评分"是哪 4 个维度？每个维度的权重分别是多少？权重是你拍脑袋定的还是有调参过程？如果用户换了一个完全不同的健身目标（比如从减脂切到增肌），历史记忆里的"减脂策略"会不会被错误地检索出来干扰当前对话？**

> 考察点：记忆评估维度的设计思路 + 记忆的时效性和情境冲突问题。

**Q18. 为什么 importance 阈值定在 0.6？如果调成 0.5 或 0.7，存储量和召回率会怎么变？有没有做过敏感性分析？**

> 考察点：阈值选择的工程严谨性。

### 4.2 评测层

**Q19. "存储噪音率从 47% 降到 15.4%"——"噪音"在这个场景里的定义是什么？谁来判定的（人工标注还是 LLM 判官）？"全量对话存储"作为 baseline 的噪音率 47% 是怎么标出来的？**

> 考察点：非标准指标的定义严谨性。这个指标是你自造的，面试官一定会问定义。

**Q20. "偏好召回 Recall@5 达 87.5%，MRR 0.71"——你召回的"偏好"是什么？测试用户有多少个？每个用户存了多少条记忆？评测时是怎么模拟"系统重启后用户重新对话"这个场景的？**

> 考察点：记忆评测的实验设计是否可信。

### 4.3 实现层

**Q21. 记忆写入 Qdrant 用的什么 embedding？和文档 RAG 用的 embedding 是同一个模型吗？记忆召回时和 RAG 检索的结果是怎么区分的（同用 Qdrant 会不会互相污染）？**

> 考察点：不同模块共用向量库时的隔离设计。

**Q22. 对话后 LLM 异步提取候选记忆——"异步"具体是怎么实现的？是 FastAPI 的 BackgroundTasks、Celery 还是别的？如果用户连续快速发消息，多条异步提取会不会产生竞态条件（比如同一记忆被写入两次）？**

> 考察点：异步任务编排的工程细节。

## 七、CareerPilot AI — 多智能体编排

### 7.1 架构设计

**Q30. 为什么拆成 5 个专职 Agent 而不是一个全能 Agent？多 Agent 相比单 Agent 多出来的开销是什么（token、延迟、状态管理）？在什么情况下你其实应该合并掉其中两个 Agent？**

> 考察点：多 Agent 架构不是越多越好，能不能说出代价是关键。

**Q31. Coordinator 根据"输入组合条件"路由——请具体说：条件是硬编码的规则（比如"有简历无 JD → 简历分析节点"）还是 Coordinator 自己用 LLM 判断？如果用户同时给了简历 + JD + "还想让我练练面试"，Coordinator 怎么编排多个节点的执行顺序？节点之间是串行还是可以并行？**

> 考察点：路由与编排的实际逻辑。

**Q32. 5 个 Agent 在 LangGraph StateGraph 里是怎么共享状态的？一个 Agent 的输出怎么变成下一个 Agent 的输入？如果中间某个 Agent 挂掉了，整个 Graph 是回滚重试还是 partial result 继续？**

> 考察点：StateGraph 的消息传递和容错。

**Q33. 简历分析、GitHub 评估、模拟面试这些 Agent 都在调 LLM，一次完整流程下来要串行多少次 LLM 调用？总延迟多少秒？你做了什么优化（并行、流式、缓存）？**

> 考察点：多 Agent 系统的性能意识。

### 7.2 MCP 工具链

**Q34. 什么是 MCP？它解决的核心问题是什么（MCP 和普通 HTTP API 的本质区别）？为什么选 MCP 而不是直接写 GitHub REST API 调用代码？**

> 考察点：对 MCP 协议本身的理解，不只在"用了 langchain_mcp_adapters"层面。

**Q35. 你说设计了解析器解决"MCP 响应多层 JSON 嵌套"问题。请给一个具体例子：MCP 返回的原始结构长什么样？你的解析器做了什么？它是通用解析器还是针对 GitHub MCP Server 特定返回结构的硬编码？如果换成另外一个 MCP Server（比如 Notion MCP），你的解析器还能用吗？**

> 考察点：这是你"工具调用成功率 100%"这句话的验证点。如果解析器是硬编码的，100% 就没什么可炫耀的。

**Q36. GitHub MCP 涉及仓库搜索、文件读取、语言统计、提交记录——如果你要评估的仓库很大（比如 10 万行代码），你怎么在有限 token 预算内做"质量评估"？你是读所有关键文件，还是只读 README + code 统计？你评估"项目质量"的维度到底是什么？**

> 考察点：大代码库评估时的 token 预算策略，这是真实会遇到的问题。

### 7.3 Redis 缓存

**Q37. 你说"对输入参数取 MD5 后缓存"——MD5 的对象是原始简历 PDF + JD 文本吗？那如果简历文件没变、但用户改了口径（"请更严格一点评分"），相同 MD5 会命中缓存返回旧结果，这个问题你怎么处理的？**

> 考察点：缓存 key 的设计粒度，缓存命中率与正确性的 trade-off。

**Q38. "响应从 15—45s 降至 <50ms"——这个 <50ms 里包含了什么？Redis 网络往返一般是 1ms 级别，那这 50ms 花在哪了？**

> 考察点：对性能数字的诚实拆解。面试官想听你说"剩余的还有序列化和后续处理的耗时"这样有洞察的答案。

**Q39. 24h 过期时间是拍脑袋定的吗？如果 JD 在 24h 内被招聘方改过，用户拿旧缓存结果会不会误事？用 Redis TTL 之外，你有想过主动失效（比如检测到文件哈希变化就删对应缓存）吗？**

**Q40. Redis 不可用时"静默降级，不阻塞主流程"——具体怎么实现的？是 try-catch 包住 Redis 调用返回 None 走原始流程？怎么防止 Redis 恢复后缓存和实时数据不一致？**

## 八、跨项目综合题（面试官最喜欢的"拉通拷问"）

**Q45. 两个项目你都用了 LangGraph，但一个是 ReAct Agent 单智能体路由，一个是多 Agent StateGraph 编排。LangGraph 的 StateGraph 和它能表达的图结构是同一个东西吗？你在 Fitness 项目里的"路由到 3 个工具"如果用多 Agent 方式（每个工具一个 Agent）重写，架构上会有什么不同？你判断两种范式各自适合什么场景？**
